# Resource Safe Execution v0.2.0 Release Design

## Goal

Publish the distribution and launch work already merged to `main` as
`v0.2.0`, with one release-pinned install path and an auditable statement of
what did and did not change.

## Chosen approach

Use a packaging-only minor release. The Codex and Claude plugin manifests
already declare `0.2.0`, so the public README, release notes, Git tag, and
GitHub release will use the same version.

The nine canonical files under `skills/resource-safe-execution`,
`skill-manifest.json`, and `SHA256SUMS` remain byte-for-byte unchanged from
`v0.1.0`. The release notes must state that the probe, safety policy, JSON
schema, and client-runtime evidence did not change.

## Alternatives rejected

- `v0.1.1`: rejected because it would conflict with the merged plugin
  manifests that already declare `0.2.0`.
- Delay the release until the probe changes: rejected because it would leave
  the public repository with inconsistent install and plugin versions.

## Repository changes

- Add `docs/releases/v0.2.0.md` as the canonical release-note body.
- Update the audited install URL and release status in `README.md` to
  `v0.2.0`.
- Replace version-qualified Windows probe wording with current-behavior
  wording, because the probe itself remains unchanged.
- Add a focused release-readiness test that enforces version consistency,
  release-note scope, and the release-pinned install route.

## Publication flow

1. Run all local validators sequentially under the low-impact resource
   profile.
2. Push a release PR and require all six GitHub Actions matrix jobs to pass.
3. Squash-merge the unchanged PR head.
4. Create annotated tag `v0.2.0` at the merged release commit.
5. Publish a GitHub release using `docs/releases/v0.2.0.md`, attaching
   `skill-manifest.json` and `SHA256SUMS`.
6. Install the tag into a temporary clean directory and compare the nine
   installed files with the tagged canonical folder.

## Failure handling

- Do not tag if local validation or CI fails.
- Do not merge if the PR head changes after verification.
- Do not publish if the tag does not point at the merged release commit.
- If a release upload fails, leave the tag intact, diagnose the release
  state, and retry only the missing release operation.
- Do not rewrite or delete the existing `v0.1.0` tag or release.

## Success criteria

- README, Codex metadata, Claude metadata, tag, and GitHub release all use
  `v0.2.0`.
- All repository tests and validators pass locally.
- All six Windows, macOS, and Ubuntu CI jobs pass.
- The GitHub release exposes `skill-manifest.json` and `SHA256SUMS`.
- One noninteractive clean install from the `v0.2.0` tag passes validation
  and matches the canonical nine-file payload.
